# 教学对话过度限制问题与调整建议

记录日期：2026-11-12。代码核对基线：`main@e6c29a9`；同时参考 C3 内容候选 `7f1cc30`。本文件整理已发现的问题和建议，不代表相关运行代码已经修复。

## 1. 目标与结论

当前交付目标是录制视频，并让评委以学生、教师身份体验功能。学生会自由上传不同章节的题目图片、补充条件和追问，不能要求其按照固定脚本或程序支持的公式格式交流。全书基础内容覆盖仍为必做项；并发、压力测试及生产级完善继续暂缓。

**开发时间优先用于修复和体验打通。** 复用已有有效验收记录，只检查本次改动直接影响的行为；同一候选版本不反复运行本地全量测试、真实模型预跑和多轮独立复审。开发检查按第 8 节的精简方式执行，产品中的独立验证教学机制继续保留。

建议保留数学工具，将其改为模型按需使用的核验能力，取消“必须完整结构化、必须由工具验算通过，才允许开始或继续交流”的门槛。工具不支持、超时或无法给出结论时，允许继续教学对话；工具与模型结论发生矛盾时，应核对题意和计算依据，未解决前保留不确定性。

图片看不清、条件缺失或暂时无法判断时，模型应直接说明具体问题、提出针对性追问，让学生补图或补充信息。正常澄清不应变成“提问提交失败”，也不应自动结束会话或立即转交教师。

继续交流、确认数学正确、确诊错因和更新掌握状态是不同动作。放开交流方式，不等于可以把不确定判断写成已核验事实。

## 2. 已确认的问题

证据分为两类：**代码确认**表示已检查相应分支，但没有逐项完成真实浏览器复现；**函数复现**表示已经运行实际判定函数并观察到结果。下表不把建议当作已实现功能。

| 编号 | 当前限制与依据 | 对体验的影响 | 建议调整 |
| --- | --- | --- | --- |
| R1 | **受理前必须完成后台解题与结构化。** 知识点不在库中、没有 `spec`、工具未返回通过、独立转写不一致等，均可能使 `solve` 返回空；随后接口返回 422，尚未创建提问任务。另有针对“某点求导”的专门拒绝规则。[S1]、[S2] **代码确认。** | 证明题、微分方程求通解、需要说明条件的题，以及部分普通计算题无法开始对话；学生也得不到具体的澄清问题。 | 先保存学生提问并进入可持续会话。知识点归类、参考解与工具核验在后台按需完成；暂时不能确定时，保持待澄清状态。不能为了建任务伪造知识点、标准答案或核验结果。 |
| R2 | **拍题沿用了“转写学生答案”的提示词。** 拍题入口复用 `transcribe_answer`，提示词要求将学生答案抄成 LaTeX；后续提问只提交文本，没有携带原图引用。[S3]、[S4] **代码确认。** | 完整题干、图形、表格、分问及附加条件有丢失风险；后续模型无法重新查看原图。 | 区分题目理解和作答识别。保留原图，允许模型结合图片与文字理解完整题意；转写可用于展示和核对，不作为唯一输入。学生不必手动整理成 LaTeX 才能交流。 |
| R3 | **识别不确定被当作提交错误。** 图片转写的 `latex` 为空时直接返回 422，即使模型可能已在 `doubts` 中说明疑点，也无法形成后续澄清对话。[S5] **代码确认。** | 学生只能重试上传或手动输入，无法顺着模型的具体问题补充信息。 | 对已经成功接收、可交给模型查看的图片，保留会话并展示具体疑问，例如“积分上限看不清，请补拍右上角”。文件损坏、模型服务不可用等技术失败仍由应用提供明确提示。 |
| R4 | **普通追问可能被当作作答。** 等待题目期间收到回复后直接进入评阅、写作答证据；在诊断阶段还会增加追问计数，没有先区分澄清或补充信息的分支。[S6] **代码确认。** | “为什么这里乘 3”“这个符号是什么意思”可能消耗诊断轮次；“补充一个条件”也可能进入错误的判分上下文。 | 在教学动作中区分实际作答、概念追问、澄清、补图和更正条件。非作答消息正常回应，不计作错误或有效作答，不消耗作答轮次；原始对话仍保存。更正条件后重新理解题目并处理旧判定的适用性。 |
| R5 | **提示等级按轮次机械推进。** 主动提问流程按 `level + 1` 给下一层提示，到第 4 层给完整解答；没有单独处理学生对上一条提示的澄清请求。[S7] **代码确认。** | 学生尚未理解当前提示就进入下一层；普通追问也可能推动完整答案出现。 | 保留“先尝试、分层提示、必要时完整解答”的教学策略，由实际学习进展决定推进。解释上一条提示、补条件和补图不推进等级；完整解答后仍安排新的独立验证。 |
| R6 | **辅导追问与练习必须是可核验的单个表达式。** 出题提示词明确排除文字解释和多项答案，模型输出与质量门槛又强制要求 `spec`。[S8] **代码确认。** | 即使入口放开，后续诊断与辅导仍不能自然覆盖证明、过程分析、完整解族或混合作答。 | 允许表达式、步骤、文字及混合作答。可计算部分使用工具；论证和条件按明确要点评阅。保留“提出假设—提出有区分作用的问题—根据实际作答更新假设”的诊断机制，并记录判断依据。 |
| R7 | **未知错因会中断当前辅导。** 模型提出未建模错因后，代码记录待审核内容并立即返回重规划；没有库内候选时也请求重规划。[S9] **代码确认。** | 内容库未预置某种错误，就难以继续当前教学；学生的交流可能被过早打断。 | 将待审核错因与是否继续交流分开。允许先作为暂定解释继续澄清、辅导，不能直接宣称已确诊或写成公共已审核错因。教师审核与真正需要教师介入时的转交继续保留，教师明确设置的轮次上限仍有效。 |
| R8 | **防套答案的匹配范围过大。** 当前拦截除题干、指纹外，还比较最终答案是否等价；不同题只要结果相同，也可能进入 409 分支。[S10] **函数复现并核对调用路径。** | 学生正常询问另一道题，也可能被当成索取当前验证题答案。 | 保护同一道或等价改写的待答验证题，不以数值巧合判定题目相同。允许不泄露答案的题意澄清；如需实质辅导，应明确转回辅导，并避免把受辅导后的结果当作独立验证通过。 |

R1、R2、R3、R4、R6 应优先处理，先保证跨题型输入与连续交流；R5、R7、R8 在接通完整诊断和验证流程时一并收尾。第一版仍应形成完整教学闭环，不能只放开入口、留下后续无法判分或继续辅导的分支。

## 3. 已复现的防套答案误拦截

两道不同题目：

- 学生新提问：`∫₀¹ 2x dx`，结果为 1。
- 尚未作答的验证题：`lim(x→0) sin(x)/x`，结果也为 1。

两题运算不同、含义不同，但实际 `same_revealed_answer` 函数返回 `True`；提问受理代码将该返回值作为拒绝条件之一。复现的是实际判定函数，不是完整浏览器／HTTP 场景。

在已配置项目隔离环境的 `backend` 目录可复现；以下代码不调用模型，也不写业务库：

```python
from app.contracts.values import ItemSpec
from app.verify.tools import SympyMathTools

asked = ItemSpec(
    operation="definite_integral",
    expr="2*x",
    bounds=[{"var": "x", "lower": "0", "upper": "1"}],
)
protected = ItemSpec(
    operation="limit",
    expr="sin(x)/x",
    variables=["x"],
    limit_point="0",
)
tools = SympyMathTools()
print(tools.verify_item(asked, "1").ok)       # True
print(tools.verify_item(protected, "1").ok)   # True
print(tools.same_revealed_answer("1", asked, "1", protected))  # True：范围过大
```

## 4. 建议的处理流程

1. **接收与保存。** 接收文字、原图和学生已有尝试，保留上下文，展示处理状态。正常教学内容不因暂时没有标准答案、知识点归类或可计算格式而被拒绝。
2. **理解与澄清。** 模型读取完整题目。图片不清、条件不足、分问不明确或确实无法判断时，直接说明具体问题并请学生补充。
3. **按意图回应。** 学生可以尝试作答、询问概念、解释自己的卡点、补图或更正题意。教学动作应与当前消息对应；模型结构化输出可用于驱动程序，但不要求学生按固定格式说话。
4. **按需核验。** 可用工具时选择合适的计算；其余由模型依据题意、推导与评分要点评阅。工具结果只对它实际处理的表达式、范围与假设负责，必须核对其是否对应原题。
5. **诊断与教学。** 保留错因候选、区分性追问、针对性辅导和分层提示。不能确定错因时继续澄清，或明确保留未确定状态。
6. **独立验证与教师协同。** 继续使用新题验证学习结果，保持验证 Agent 的信息隔离。教师查看证据、接管、交还、覆盖计划和处理待审核错因的能力保持有效。

模型调用失败和模型正常回复“暂时无法判断”应分开处理。前者没有可用模型回复，由应用提示重试并保留已接收内容；后者是正常对话，可以直接向学生解释。

## 5. 数学工具的建议定位

建议保留现有数学工具和题库数学检查，优先复用已实现的工具调用能力，而非删除整个核验模块。

- 模型负责理解题意、组织交流和选择教学动作；工具提供可重复计算的依据。
- 普通澄清和概念交流应尽快回应，避免无必要地串行执行多轮求解、转写和审核；涉及实际判分、争议核对或重要学习结论时，再开展相应核验。
- 是否能完整转换为 `ItemSpec`，不决定是否允许继续交流。
- 工具不支持、报错、超时或返回无法判断时，可以继续解释和教学；不得将其记录为“工具已核验通过”。
- 工具与模型结论冲突时，核对原题、转写、定义域、边界与计算。未能解决时说明当前疑点，保留不确定结论；不能无条件忽略矛盾。
- 证明、微分方程通解等题目可组合使用模型论证评阅与局部计算。检验几个特例不能冒充一般性证明，解代回成立也不自动证明通解完整。

本建议依据本项目已有能力与当前体验目标，不依赖“模型永远不会错”或“工具永远更可靠”的假设。

## 6. 需要保留的规则

| 保留项 | 目的与调整边界 |
| --- | --- |
| 登录、角色权限、学生及附件归属 | 学生的题目、图片和对话只进入其有权访问的会话。 |
| 当前题目与作答轮次绑定 | 防止旧图片、旧回复写入另一道题；更正题意时应显式更新上下文。 |
| 教师指令优先、接管与交还 | 放开自然交流不能绕过教师对该学生教学动作的控制。 |
| 原始作答与证据可追溯 | 保存学生实际输入，区分对话、实际作答与判断依据；模型评阅不能冒充工具核验。 |
| 掌握状态与独立验证隔离 | 学生说懂了、辅导时做对、模型给过答案，不自动等于掌握。 |
| 有限的文件和调用资源约束 | 保留服务承载边界；优先通过压缩、清晰的上传提示和合理重试改善体验。 |

先尝试、分层提示、独立验证和必要时转交教师属于产品教学机制。建议调整其执行时机与消息处理方式，不直接将其全部删除。

## 7. 改动范围与实施顺序

按当前代码看，属于中等规模的集中调整，主要涉及十来个核心文件，另有必要的契约、生成类型和少量回归用例。具体文件数与改动行数需在实施方案固定后统计，不能将其理解为已经完成的工作量估算。

| 范围 | 主要调整 | 可复用部分 |
| --- | --- | --- |
| 图片输入与模型消息 | 正确理解题目、保留原图引用、支持后续补图，改造题目上传和会话展示 | 已有多模态 `ChatMessage`、图片模型接入、学生和教师页面 |
| 提问受理与会话状态 | 先保存输入，支持待澄清、待归类、未完成求解的状态，再关联正式教学任务 | 已有编排、checkpoint、SSE 和任务队列 |
| 辅导 Agent 与提示推进 | 区分作答和普通交流，支持文字／多项结果，未知错因允许继续沟通 | 已有错因库、策略、假设及分层教学能力 |
| 核验与判分 | 工具按需使用，补齐无 `spec` 的评阅路径，修正防套答案匹配范围 | 已有工具调用循环、验证 Agent 的模型评阅及解释题 rubric |
| 证据与接口 | 如实记录判定来源，必要时为附件与新状态扩展兼容字段，同步 OpenAPI 与前端类型 | 已有账本、权限、契约与生成流程 |

### 第一阶段：让图片与对话顺畅进入

处理 R1、R2、R3：保留原始输入，题目未理解完整时可以正常澄清，工具不支持时不拒绝开启会话。既有任务要求关联知识点，实施时须处理待归类会话与正式任务的关系，不能随意填入一个知识点或伪造标准答案。

### 第二阶段：让教学过程兼容自然交流

处理 R4、R5、R6、R7：补充作答与普通交流的区分，调整提示和轮次推进，打通非单表达式的诊断、练习与评阅。保留原有教学闭环，避免只把系统改成直接输出完整解答的问答框。

### 第三阶段：接通验证与证据，完成体验预跑

处理 R8，接通判断来源、教师控制、历史消息与新题验证。完成第 8 节的三条体验路径，集中提交后执行仓库 CI；不额外重复本地全量检查。

删限制与补替代路径要在同一轮完成。例如，现有后续代码直接使用 `item.spec.answer_mode`，仅删除入口的空值拒绝会造成后续失败；当前 `_record_attempt` 还根据结果是否为空选择工具／模型来源，支持模型判对判错后必须改为依据实际判定来源记录。[S11] 不宜采用“先批量删判断，再观察哪里报错”的做法。

## 8. 精简验证与交付标准

### 修改过程中：只做直接相关的检查

- 每次修复优先运行已有的相关测试。对确实容易再次出错的行为，补一个能覆盖实际问题的最小回归即可；不为简单文案、样式或复述实现的改动新增测试。
- 已经核实的代码事实、C3 内容覆盖和既有验收结果直接复用，不重新整套验证。
- 不默认安排多轮独立复审、逐层截图、全量数据库导出或每条消息的编号举证。记录版本、体验结果和实际失败点即可。
- 出现新失败、修改影响范围扩大或仍有具体疑点时，才追加对应检查。通过后继续交付，不为了“更放心”反复重跑。

### 交付前：合并跑通三条体验路径

| 体验路径 | 最少要确认的结果 |
| --- | --- |
| 学生自由提问 | 选一张计算题图片和一张证明题或微分方程图片，实际提问、追问并补充信息。模型能正常回复和澄清，普通交流不被误记为错答或消耗轮次。 |
| 学生完成教学流程 | 走通一次诊断、分层辅导和同类新题验证，判断来源记录真实。防套答案的已知误拦截修复用定向用例确认，不另起一轮完整预跑。 |
| 教师体验 | 教师能看到学生及相关依据，完成一次接管与交还，学生端响应对应变化。 |

三条路径可合在一次真实体验中完成。仅在本次修改涉及恢复逻辑时补一次重启检查；不展开故障时点、日期和轮次的组合验证。遇到实际问题再查相应日志或持久化记录，不将页面、API、SSE 和数据库的逐层重复检查作为默认步骤。

最终候选集中提交后完成仓库 CI，不在其前后重复执行同一套本地全量测试。CI 失败或后续代码变化时，按实际影响处理。未跑通的真实体验如实记录，优先修复影响使用的问题。

本轮暂缓并发压测、多实例改造、40 人全班故事数字对齐、生产级完整性验证和全面题型组合测试。全书内容覆盖直接复用 C3 的既有检查；当前重点是学生能自由提问、教学流程可继续、教师能介入。

## 9. 与当前交付的关系
